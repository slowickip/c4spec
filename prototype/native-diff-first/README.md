# Native LikeC4 diff demo

This demo exercises the two-step review flow in a scratch directory.
The canonical architecture remains
[the mini-project shop model](../../examples/mini-project/architecture/shop.c4).
No second model or mandatory per-change JSON is tracked. The rehearsal
copies that source into temporary workspaces and appends a **native LikeC4
`diff` block to the same `.c4` model file**.

Uses **published LikeC4 1.61.0**; older 1.60.0 does *not* parse `diff`.

## Review the red/green proposal locally

From the C4Spec repo root:

```bash
python3 prototype/native-diff-first/rehearse.py --out /tmp/c4spec-native-diff-pilot

cd /tmp/c4spec-native-diff-pilot/proposal
npx --yes likec4@1.61.0 start
```

Open the `shop-overview` or `notifications` view. Select
**Replace the notification consumer** (`replaceNotifications`) in the model
state menu and switch between
**As-is**, **Changes** (old node red, new node green) and **To-be**.
The review uses the **same** existing view IDs and L2 titles. Nothing in
the canonical source has yet been deleted or added.

The script writes:

- `proposal/architecture/shop.c4`: existing source + references to the
  proposed node + one native `diff` (the proposal for review)
- `dry-run.txt`: native apply dry-run output with no source mutation
- `applied/architecture/shop.c4`: scratch copy after `likec4 diff apply`;
  removed worker/relations gone, V2 worker/relations materialized, diff removed
- `stale-reference/` and `overlapping/`: intentionally invalid cases
  proving fail-closed removal and the explicit overlap gate
- `summary.json`: observed commands/outcomes/paths, **not** human approval

CI exposes the teaching fixture in the Actions job summary and artifact. The
separate diagram workflow compares rendered views at the merge base and PR
head, rehearsing pending native changes in scratch. For same-repository PRs,
it posts one visual comment with downloadable PNGs when diagrams change and
clears the comment if those changes are reverted. GitHub's Files changed tab
shows the source patch.

Download the `native-diff-as-is-changes-to-be` artifact from that CI run and
open `review-site/index.html` for the actual interactive red/green overlay.
It also contains the proposed and applied sources, native `diff-list.json`,
`dry-run.txt`, `summary.json` and `review-comment.md`. Artifacts expire
after **7 days** and should be regenerated by a fresh CI run. No generated
assets are committed as canonical architecture.

## Inline red/green overlay in the rehearsal summary

`inline_diff.py` renders the native fixture diff as a Mermaid block in the
Actions summary so a reviewer can see removed and added nodes and relationships
without downloading the HTML artifact. It derives the overlay from the
`.c4` model.

Inputs are provider output only — `likec4 export json --skip-layout` of the
proposal (As-is) and of the scratch `diff apply` copy (To-be), plus
`likec4 diff list --json`. Node and edge identity is matched across the two
exported view graphs (not inferred from counts), and the derived per-view
added/removed/modified totals **must equal LikeC4's own numbers** for that
diff, including effective edges removed with a deleted node. A mismatch, an
unsupported view type, a change with no visible delta, more than two views or
an oversized graph is a refusal: the summary then reports that the overlay is
unavailable and retains the counts and artifact for review.

Known limits of the spike, all deliberate:

- The diagram is an approximation of the native layout: node shapes, nesting
  and edge labels come from the JSON export, but positions and the exact
  LikeC4 styling do not. The interactive artifact stays the visual truth.
- **Containment is validated, not repaired.** If a node is a child of two
  different containers across As-is and To-be, or the hierarchy is cyclic, the
  overlay refuses: Mermaid would have to emit the same node twice or drop it.
- **Parallel relationships are only re-matched when unambiguous.** A single
  relabelled edge between two endpoints is a modification; two or more distinct
  candidates on both sides is refused, because the provider reports totals only.
  Measured upstream limit: two relations between the same endpoints collapse
  into one view edge labelled `[...]`, and rewriting both titles is reported as
  one *modified* edge while the exported edges stay identical — such a change is
  refused rather than guessed.
- At most two views, 40 nodes and 80 edges per view; landscape roll-up views
  (aggregate edges only) rank last and are used only to fill a spare slot.
- Derived Mermaid cannot express LikeC4 decorations such as icons, badges or
  relationship kinds; those remain visible only in the native rendering.
- LikeC4 1.61 has **no diff-aware Mermaid/markdown export** (`gen mermaid`
  renders As-is only, measured), so no upstream switch can replace this.
- Prose outside the Mermaid fence is escaped separately from diagram labels:
  a view title cannot open a link, start emphasis, or mention a user.

## Intended real-project sequence

1. **On a feature branch**, author `diff changeName { remove {} add {} }`
   alongside the canonical `.c4` model, without modifying its current nodes.
   A view may reference a proposed node: As-is ignores it, To-be includes it.
2. Pin exactly 1.61.0, run `likec4 validate`, `likec4 diff list`, then
   `likec4 diff apply changeName --dry-run`. Review As-is/Changes/To-be,
   source patches, affected relationships and any overlapping diffs.
3. **After explicit design/implementation authorization**, implement
   authoritative code/IaC/tests. On the branch, apply the native diff only
   when the intended architecture really becomes current. Validate the
   resulting model, re-run the actual tests and compare to the reviewed
   proposal. Re-review any material divergence.
4. **Human PR approval and merge** advances the canonical model and code
   together. No long-lived red/green annotation or second model is committed.

Native `apply` deletes the diff's title, rationale and comments, so a material
decision must be retained in the PR/commit or a durable ADR when warranted.
A rename that doesn't alter the architectural identity should **not** create
two artificial nodes.

## What this pilot does not claim

- Tests are scratch-fixture proof, not a deployed worker, automatic human
  approval, GitHub-rendered interactive diff or production runtime verification.
- The legacy optional `change.json` schemas and `diff.py` remain for
  behavior/constraint cases and 1.60.0 consumers. They are **not** required for
  architecture-only native diffs; remove redundant machinery only after a
  measured migration.
- C4Spec owns the bundled [DSL/CLI guidance](../../.agents/skills/c4spec/references/likec4/README.md)
  and validates exactly 1.61.0. Future releases require the documented upgrade
  checks; the upstream skill is a provenance source, not a runtime dependency.
